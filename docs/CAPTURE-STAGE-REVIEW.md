捕获阶段设计 85 分：**核心裁决（零摩擦压倒一切、结构全部后置）正确且

## 二、最终要求 v2（2026-09-10 与用户逐条核对定稿）

### A. 核心红线（不可协商，任何优化不得违反）

| # | 要求 | 验证方式 |
|---|------|---------|
| A1 | **零摩擦第一**：任何通道从"想记"到"记下"≤ 3 秒，无任何必填项 | 每条通道实操计时一次 |
| A2 | **机器只接不判断**：捕获时刻不分类/不摘要/不改写/不写 frontmatter | 落地文件为裸 md，与输入一致 |
| A3 | **落地即普通文件**：人可读、脱离系统可打开；入口互不知晓（文件级解耦） | 直接 cat 文件可读 |
| A4 | **成本后置**：LLM/API 只花在过了确认门的内容上，捕获时零 API 调用 | 日志无捕获期 API 请求 |

### H. 归档两层级（用户问题 2 的澄清，属第⑤环，记录在案）

- 处理产物先落 memory/ 根（收件箱，带「待确认」）——中转站不是归档；
- 确认后归 memory/ 子目录（平台/书籍<分类>/日记/想法/目标）：Obsidian
  手动拖 或 飞书卡片「📁 归档…」（机器推导推荐，人点定才移动）；
  **机器绝不自动归档**（红线）；
- 再深一层：wiki/ 才是真沉淀（永久不衰减）；trash/ 是遗忘出口。

## 三、记账不改的小风险

- 15 分钟处理时滞：捕获的成功标准只是"接住"，时滞不影响捕获本身。
- Syncthing 单点同步：挂了本机积压，恢复自动追平，有韧性。

## 四、明确不该改的（防御性意见）

- 不给捕获加任何必填结构（摧毁第一优先级）。
- 不在捕获时自动摘要/分类（那是阶段③的活，且白烧 API 成本）。
