## 一、总体结论（评审部分）

捕获阶段设计 85 分：**核心裁决（零摩擦压倒一切、结构全部后置）正确且
执行到位，五条需求互相自洽，无结构性错误**。扣的 15 分全在"捕获的
下游效应"——以下建议全是加法，不动主干。

系统性风险：零摩擦捕获的代价是囤而不处理（Collector's Fallacy）。
现有对策全在后端（待确认门、decay 遗忘、晨报提醒），捕获端缺"轻量
意图信号"——剪藏/转发瞬间"为什么存这个"最鲜活，到确认环节已忘大半。

## 二、最终要求 v2.1（2026-09-10 与用户逐条核对定稿）

### A. 核心红线（不可协商，任何优化不得违反）

| # | 要求 | 验证方式 |
|---|------|---------|
| A1 | **零摩擦第一**：任何通道从"想记"到"记下"≤ 3 秒，无任何必填项 | 每条通道实操计时一次 |
| A2 | **机器只接不判断**：捕获时刻不分类/不摘要/不改写/不写 frontmatter | 落地文件为裸 md，与输入一致 |
| A3 | **落地即普通文件**：人可读、脱离系统可打开；入口互不知晓（文件级解耦） | 直接 cat 文件可读 |
| A4 | **成本护栏**：捕获时刻零 API 调用；LLM 只在处理阶段按护栏运行（每篇至多一次、超长跳过、失败降级、确认卡不含正文全文） | 日志无捕获期 API 请求 |

**转化笔记归类（三步走，归档永远人动手）**：

1. 产出落 memory/ 根（收件箱，带「待确认」）——中转站不是归档；
2. 确认后归 memory/ 平台子目录（抖音/小红书/B站/飞书/媒体/书籍<中图法
   分类>/日记/想法/目标）：Obsidian 手动拖 或 飞书卡片「📁 归档…」
   （机器推导推荐，人点定才移动）；**机器绝不自动归档**（红线）；
3. 值得长期留的进 wiki/（真沉淀，不衰减）；trash/ 是遗忘出口。
   PDF 特例：划重点勾中项直接进 wiki 摘录卡（不经 memory 待确认）。

## 三、记账不改的小风险

- 15 分钟处理时滞：捕获的成功标准只是"接住"，时滞不影响捕获本身。
- Syncthing 单点同步：挂了本机积压，恢复自动追平，有韧性。

## 四、明确不该改的（防御性意见）

- 不给捕获加任何必填结构（摧毁第一优先级）。
- 不在捕获时自动摘要/分类（那是阶段③的活，且白烧 API 成本）。
